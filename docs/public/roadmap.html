§ 01

The product

A floor-plan editor that runs entirely in a browser tab.

You draw walls on a plan, and the same building appears in 3D beside it. Rooms are found from the walls rather than declared; doors and windows are cut into walls as parameters rather than placed as meshes; furniture comes from a catalog of 217 models. There is a walk-through camera, a sun you can put where you like, textures and colours on any surface, stairs and structural members, multiple storeys, a roof, dimensions and text labels, undo, and a link that carries a whole design without a server.

There is no server, no account and no database. Designs live in the browser's own storage and go out as a compressed link or a file. Nothing is uploaded, and there is nothing to log into — which is a design decision, not a missing feature, and it is why this document has no section about security posture beyond a dependency policy.

What it is

A library — the document model, the 2D plan and the 3D viewer — that an embedder can use on its own, and an application built on top of it that is the thing most people mean by architect3d.

Published as ESM and IIFE, with three and bezier-js as peer dependencies and no runtime dependencies of its own.

What it deliberately is not

Desktop web only. A phone-and-tablet programme was drawn, priced at 2.5 weeks and withdrawn, so the audience is a decision rather than an omission.

English only. A localisation sprint was built and reverted whole.

Not published, not deployed. Both are ready and waiting; see § 06.

THE RULE UNDERNEATH ALL THREE

A bundler splits on a boundary in the graph, not on a predicate over paths. A manualChunks function that offers to put three somewhere else does nothing while one constructor still writes new Main(...); the import has to actually stop existing. Every seam above is a real dynamic import, and each is checked by something that counts what a boot downloads rather than by reading the config.

§ 03

What actually gates

Fourteen checks run without anybody asking. Seventeen more exist as commands, and this is the first document to say which is which.

The design principle has not changed and is still right: Actions minutes are the constrained resource, so cheap high-yield checks run on the machine that made the change and only what genuinely needs a runner is paid for. What follows is what is wired up, read out of lint-staged.config.mjs and .github/workflows/ rather than from any previous description of them.

Tier 0 — the pre-commit hook

Runs on every commit, on the staged files, in about two seconds. Installed by npm run prepare and skippable with --no-verify, because a gate with no override gets disabled wholesale.

Tier 2 — the browser job, in parallel

267 tests in 39 files, chromium only, one file at a time. Deliberately not needs: the first job: if the data layer breaks and the renderer also breaks, both are worth knowing in one run.

What it is for is the three things jsdom cannot do: the 2D plan rasterised and its palette read back off the canvas, the 3D view composited through SwiftShader and read with readPixels, and axe over the booted application. Since Q3 it loads the real stylesheet, which is what makes the third of those mean anything — see § 07.

Two workflows that have never run

deploy.yml waiting

Builds, checks, publishes to Cloudflare Pages and runs Lighthouse against the published URL. Needs CLOUDFLARE_API_TOKEN, an account id and a Pages project. Blocked on a credential, not on work.

publish.yml waiting

npm trusted publishing over OIDC with --provenance, no long-lived token. Dispatch-only and defaults to a dry run, because a publish is the only irreversible thing here. Blocked on a decision.

§ 05

What must not change

Six rules. Each is here because breaking it has cost something, and each is enforced by code rather than by memory.

A floor is a ratchet

No coverage threshold and no Lighthouse floor moves down, ever. A limit may move up with the measurement written beside it, and vitest.config.mjs carries that history inline. When a change genuinely cannot be covered, the file is excluded explicitly, with a reason, so the exemption is visible in review rather than hidden in a lowered number.

The corollary a whole sprint was spent learning: round the measurement down, strictly. A floor set at exactly its own measurement has no headroom at all, and the one time that happened the gate failed seven runs in twenty-one on an unchanged tree.

Four preserved bugs, pinned and named

src/scripts/core/utils.js has four call sites passing arguments in a signature that no longer exists. JavaScript discards the extras; the type checker does not, so each is pinned with @ts-expect-error and a ledger states the consequence, verified by running it:

FunctionWhat it actually returns
pointInPolygonalways false
polygonPolygonIntersectalways false
polygonInsidePolygonalways false
polygonOutsidePolygonalways true
pointInPolygon2correct — the sibling nobody refactored, and the one everything calls

They are behaviour a working product depends on. Tests named PRESERVED BUG hold them. Do not fix them.

A characterization failure is a signal to re-check the change

The library suites describe what the code does, not what it should. Several behaviours are quirky and load-bearing. When one fails during a refactor, the expectation is not the thing to edit.

The frozen goldens cannot be regenerated

The r98-era baseline fixtures are reference inputs captured before the migration, from a toolchain that no longer exists. Their counts are deliberately concrete: if one changes, the model layer changed, and that is a decision to make on purpose.

Measure, do not quote

Every number in this document came from running something. Re-run a predecessor's figure rather than subtracting from it — a figure derived by subtraction has been wrong here twice, and both times the arithmetic was fine and the baseline was not. A number later found wrong is corrected in place beside the original, not overwritten.

The save format is a public contract

Designs already exist. Texture URLs are serialized into saved documents, so a file under public/rooms/textures/ cannot be renamed without breaking plans somebody has already made. Five programmes running have not touched the format.

§ 06

What is open

Two items. Neither decision is engineering work, and both are stated plainly rather than being allowed to look done. What is engineering work is making sure the decision is taken against real numbers, and on the second item it had not been — see AC-5 below.

Nobody has opened it M-51

This application has never been used by anybody who is not holding this repository. There is no hosting account, so the deploy workflow, its checks and its Lighthouse floor are all built and waiting on a credential.

Every claim here about a deployed product is a projection. Eight drawings have said so in the same words.

How large the catalog should be for the owner

217 models today. A budget line was quietly deciding this by accident until it was re-derived from what it was actually protecting; the constraint is gone and no answer replaced it. It is still a product decision, not an engineering task — but RM-020 AC-5 re-derived what the decision is being taken against, because both figures this section used to publish were wrong.

What it said, and what the tree says. This section read “room for roughly 930 rows inside the current index limit” and, in tools/budget.json, “608 more models” of public-total headroom. Neither survived measurement, and they were wrong in opposite directions:

So the answer, on measurement: the catalog can roughly double. public-total binds first, at 212–366 more rows depending on what is curated — call it 430 to 580 total. The index budget is nowhere near binding and will not be until about 1,630. The drawer would then hold 430–580 rows in the DOM, which no browser will struggle with and no budget line watches.

The correct number was already in the repository. tests/catalog-cost.test.js has computed exactly this division since RM-012 J2 — headroom / REPORT.totals.mean — and has been green on 212 the whole time this section published 608. The right answer lived inside a test and the wrong one inside a document, and nothing connected them. catalog-cost.mjs now writes totals.capacity into its report, so the quotient is generated where the divisor is maintained; the table above cites it rather than re-deriving it, and a new case asserts the report and the tests agree.

Two more things are true and are not tasks. Four floors are within two units of red, two of them at zero — visible on every CI run rather than discovered by a red build. And the source maps in the published package are 66.7 % of it, waiting on somebody to decide whether a consumer should get readable stack traces at that price.

WHAT THE FIXES CHANGED, AND WHAT THEY DID NOT

Eleven fixed, one blocked upstream, one withdrawn as wrong, and one — S-12 — half of each. Three of the fifteen therefore did not survive contact with the code, which is the number worth remembering about a review conducted by reading. Two of them changed behaviour rather than tidying it, and both are worth knowing about. S-1 means a torn-down design now gives its meshes back — the data still serializes, which is the half the old note was right to protect. S-3 means the library’s spin: true default now actually rotates the model, which it has not done for as long as the render loop has been on demand; the application calls stopSpin() at boot and is unaffected, but an embedder on the defaults will see a difference. Neither costs a frame while nothing is happening: update() reports no change on a settled scene, and the idle-frames assertion holds it there.

S-5 was deliberately left part-done in the first pass — two composables of twenty-two — and finished in a second, on its own, which is what a refactor of the composition root deserved. Fourteen are injected now and eight remain props by the same rule that selected the fourteen: a component taking one or two values from a composable is not being drilled through. App.vue went 92 props and 72 events to 28 and 32. What the conversion cost was six test files, each of which had been mounting a component with props it no longer takes. It was reported at the time as “both tiers green throughout”, and that was true and not sufficient: the sprint after it ran ledger:check and found 36 type errors S-5 had let in, because eleven components had left the type check without either tier noticing. That is S-16, and the honest version of this paragraph is that S-5 shipped green on the gates it was watched by.

And two findings were produced by the fixing rather than by the audit: S-15 and S-16, below.

S-12 turned out to be the same shape as S-1, one directory over. Its legacy-json/ half was withdrawn — that directory is the oracle the whole S3 conversion proof rests on, and moving it aside fails 28 tests. Its .blend half was fixed, but for a reason the audit never gave: those three files are the authoring originals of the two models RM-012 J2 deleted because nobody could establish their licence, and J2 removed the derived files while leaving 21.95 MB of source sitting beside them. The assertion that should have caught it existed and passed, because it asked whether a withdrawn name was gone from public/ — the directory the derived file had been in. Twice now the hole has been at the edge of a check rather than anywhere without one.

S-15 · FOUND WHILE FIXING S-1

Writing the test that proves a torn-down design still serializes turned up something the audit had missed: it did not. FloorplannerView.dispose() disposes the carbon sheet, CarbonSheet.dispose() calls clear(), and clear() resets all eight of the fields the save format carries — so tearing down the 2D view deleted the underlay from the next save: its URL, its placement, its scale and its transparency, each set by hand and each gone without a word. The plan keeps a copy now, taken on the way out and preferred by exportSerialized only when the live sheet is gone. fixed

Worth recording for what it says about the method rather than the bug: the audit read the code and found fourteen things; writing the test for the first of them found a fifteenth that reading had not.

S-16 · FOUND WHILE FIXING S-12 — ELEVEN COMPONENTS HAD LEFT THE TYPE CHECK

npm run ledger:check came back with 36 errors against a ledger that allows none, in PlanOverlay.vue, StatusBar.vue and TopBar.vue. None of them were S-12’s doing: stashing the work and re-running proved the red had shipped in S-5, the commit before.

The mechanism. tsconfig.json states the rule plainly — a file joins the check by putting // @ts-check on its first line, or for an SFC on the first line inside <script setup>. S-5 added injection imports to eleven components by inserting them at the top of the script block, above the pragma. One line lower, and a directive is an ordinary comment. All eleven silently left the type check: AppWorkspace, ImportModelDialog, LevelSwitcher, PlanOverlay, ProjectLibrary, SceneOverlay, ShareDialog, StatusBar, ToolRail, TopBar, TourGuide.

Why nothing failed. npm run typecheck passed because it had stopped looking at them. type-coverage.test.js passed because it asks whether the text @ts-check appears in the file, and it still did. Two gates agreeing, both reading the same dead pragma. Only ledger:check — which runs the compiler with --checkJs and therefore ignores pragmas entirely — could see it, which is exactly the property RM-005 C2 built it for.

What was hiding behind it. Thirty-four of the 36 were one cause: useZoom2D and usePlanStats hand-rolled their injection before S-5 generalised it, and neither carries the @returns annotation createInjection’s twelve do. Their keys are plain Symbols, so inject(key, null) infers null, the throw-guard narrows that to never, and every property read off the result is an error. The other two were drawTarget, a shallowRef(null) that narrowed the same way.

And one was a real defect. TopBar rendered its unit dropdown from display.unit.values — the S-5 conversion had rewritten props.units by prefix-matching props.unit and leaving the trailing s. display.unit is a ref, .values is undefined, and v-for over undefined renders nothing, so the display-unit control shipped with no options in it. Measured, not inferred: with the old expression restored the new test reports 0 options where there should be 5. The same prefix-matching mistake produced S-14, one sprint earlier. fixed

Both holes are closed. type-coverage.test.js now asserts the pragma’s position rather than its presence, and app-shell.test.js mounts the shell and counts the options — because a dropdown can also empty out for reasons a type checker cannot see. What this says about the method is worth more than either fix: S-15 came from writing a test, and S-16 came from running a gate that the change under review had no reason to touch.

THE ONE THAT LOOKED CRITICAL AND WAS NOT

Four polygon predicates in core/utils.js are pinned broken with @ts-expect-error: pointInPolygon is constant-false, polygonOutsidePolygon constant-true, and FloorItem branches on both. That reads as a critical defect until you find that the file already states the exact consequence, characterization tests pin it, and RM-012 J4 shipped a correct replacement — polygonsOverlap, written from the separating-axis theorem — for the path that needed one. Preserved deliberately and correctly. All that was left of it is the wasted work in S-11.

WHAT THE AUDIT CHECKED AND DID NOT FIND

No deprecated three.js call anywhere in live code — every hit for Geometry, Face3, addAttribute, outputEncoding, THREE.Math and the rest is a comment recording a migration already done. No Options API and no Vue 2 idiom: all 29 single-file components use <script setup>. Six uses of any in 166 files, each with a stated reason. Main.dispose(), Floorplan3D.dispose() and the forceContextLoss() call are thorough. Three, Vue, ESLint and Tailwind were each already on the exact latest release.

WHAT S-1 SAYS ABOUT THE GATE LADDER

resource-lifecycle.test.js covers update(), reset(), the 3D projection, each dispose() in isolation and per-item removal. It had no whole-teardown case, which is exactly where the hole was. RM-003 A0 made disposal a boundary rather than a habit; the boundary was never asserted at the outermost edge, so the one place with no test was the one place that leaked.

THE METHOD, WHICH IS THE PART WORTH KEEPING

Every one of those drawings measured before it planned, and a measurement overturned the plan in nine of eleven cases — sometimes by removing work, twice by removing a whole programme. Three findings were recorded as nothing to do here and cost nothing but the probe. The habit that produced all of it is small: write the acceptance clause as a check rather than as a task, then run it before believing it. Twice that turned up a second instance of a defect the drawing said was unique, and five times it caught an assertion that was measuring the wrong thing.
