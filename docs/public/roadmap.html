The good news: the library core is in better shape than its toolchain. The data layer (model/, core/) is clean, headless, jQuery-free ES6 with a well-defined event backbone (THREE.EventDispatcher — API unchanged in r185). The hard, valuable algorithms — room detection, DCEL half-edge walls, corner merging — use only Vector2 math that survives untouched. The migration is mostly re-hosting, not rewriting.

The hard parts are exactly four: (1) the Geometry/Face3→BufferGeometry rewrite in six mesh-builder functions plus the model-loading merge pipeline; (2) 25 furniture models in the pre-r99 JSON format that no modern loader reads — they need one-time offline conversion to glTF, plus a URL-rewrite shim so old saved designs keep loading; (3) color-management and lighting semantics changed under us (r152/r165) — handled with an explicit two-phase strategy: pixel-parity freeze first, deliberate modernization later; (4) the demo UI is a 45 KB jQuery/dat.GUI monolith that becomes the Vue 3 app — its complete feature inventory and API contract are catalogued in this document so nothing is lost in translation.

What is already right

  • Clean layering. No model file imports floorplanner/ or three/ — the single cross-layer edge is scene.js → items/factory.js; dependencies otherwise point strictly downward. The data layer runs headless (its only environment touches are the asset loaders and Math.random in id generation) and is unit-testable as-is.
  • Stable event contract. All cross-layer communication uses THREE.EventDispatcher + 38 string constants (core/events.js). EventDispatcher is unchanged in r185 — the entire backbone survives.
  • The hardest code needs no rewrite. Floorplan.findRooms (tightest-cycle room detection), Room.updateWalls (DCEL ring), HalfEdge.halfAngleVector (wall offset outlines), corner merge/split — all pure Vector2 math on APIs that still exist. These files get frozen semantically and re-hosted verbatim.
  • ES6 source throughout. No transpile step is even needed for modern browsers — Babel 6, its presets, and most of the rollup plugin chain simply disappear.

The bundle pathology

The 4.3 MB bundle contains three full copies of three.js (~3.3 MB, 77%): the root r98, plus a private r94 nested under @calvinscofield/three-objloader and a private r96 under three-reflector2 — their ^0.94/^0.96/^0.98 ranges can never dedupe under 0.x semver, so rollup bundled each copy. Beyond the size, this is a latent correctness bug: instanceof checks silently fail across copies. Full unminified jQuery adds another 0.28 MB. Replacing the wrapper packages with three/addons (S4) and dropping jQuery (S2) collapses the bundle to one shared three. Done: the unminified library build went 3,318 KB → 1,988 KB (gzip 643 → 408 KB) when the four repacks were dropped in S4.

Serialization landmines (schema must survive bit-for-bit)

  • Design files (.blueprint3d) store corner coordinates in the active display unit (meters under stock config) — save/load through cmToMeasureRaw/cmFromMeasureRaw, rounded (not truncated) to 3 decimals, and the file records no unit. Reproduce exactly; do not "fix" to canonical cm. S0 finding: the mirror case is worse than a scale error — a metre-era file loaded under cm shrinks the plan below cornerTolerance (20 cm), so every corner merges into one and the design collapses. Inch round-trips also drift (0.393700 and 2.5400013716… are not inverses).
  • S0 finding — Version.isVersionHigherThan is inverted, not merely oddly typed. It evaluates file ≤ check, so a newer file (0.0.3) fails the gate and silently discards a/b/wallType — curved walls from a future file load back straight. Any forward-compatible schema work must fix this deliberately, with a test.
  • S0 finding — loadFloorplan does not no-op on a malformed file. reset() runs before the validity check, so loading null/{} destroys the current design and dispatches no EVENT_LOADED. The Vue app must validate before calling it.
  • item_type numeric registry (factory.js:10: 0,1,2,3,4,7,8,9) is written into every save file — freeze it.
  • wallType serializes the Symbol description ("STRAIGHT"/"CURVED") — the es6-enum replacement must keep producing these strings, gated behind the version check.
  • model_url is a literal relative path baked into saves — the S3 shim rewrites models/js/*.js → models/js-glb/*.glb at load so old files stay loadable indefinitely.
  • Headless hazard: loading a design with a carbonSheet block throws if no 2D view is attached — guard when the library runs widget-mode.

Reactivity discipline (the one Vue-specific trap)

Model objects (Wall, Corner, Room, Item…) rely on object identity — === comparisons in merge logic and EventDispatcher listener dedup. Wrapping them in Vue reactive() proxies breaks both silently. The rule, enforced by convention and a lint note: model instances cross the store boundary only via markRaw/shallowRef; reactive state is limited to plain UI slices (displayUnit, floorplannerMode, viewMode, selection {type, object:markRaw}, camera flags, catalog visibility). The library's own events — not deep reactivity — trigger UI updates, exactly as dat.GUI's updateDisplay() dance does today, minus the dance.

Deployment

The committed-build/ + git subtree gh-pages pattern dies. Replacement: GitHub Actions on push to master — npm ci && vite build --base=/architect3d/ → actions/deploy-pages. Runtime asset URLs are relative strings, so publicDir keeps them working unchanged under the project base path.

§ 05 · STRATEGY

Migration strategy

1 · One variable per sprint

Toolchain, then library hygiene, then assets, then engine, then UI. When the three bump lands (S4–S5), the UI around it is the unchanged legacy demo — any regression is attributable to the bump. When Vue lands (S6–S7), the engine under it is already proven. No sprint changes two of these at once.

2 · A parity oracle before anything moves

There are zero tests today. S0 builds the safety net first: characterization tests over the headless model layer (serialization round-trips, room detection, wall splitting) plus frozen design fixtures and golden screenshots from the live legacy app. Every later sprint regresses against it.

3 · Big-bang three bump — inside one milestone

Staging at r125 buys nothing: everything hard either breaks at r125 (Geometry, JSONLoader) or after it (color management r152, lights r165, WebGL2-only r163, API renames r151) — an intermediate stop doubles the visual-QA passes and targets a 2021 API we'd immediately re-touch. The breakage surface is fully enumerated (§02), so the jump is executed as one two-sprint milestone with the work sequenced inside it.

4 · Assets convert before the engine moves

The .glb conversions load fine on the old r105-era loader too — so S3 lands them while everything else is stable, retiring the JSONLoader path before the bump. S4 then deletes a loader nothing uses, instead of doing a format migration mid-bump.

Two-phase look management. The r185 default look (sRGB output, physical lights) is a genuine improvement — but adopting it during the bump would make "is this a bug or the new color pipeline?" unanswerable during QA. So the bump itself (S4) freezes the r98 look (ColorManagement.enabled=false, linear output, lights ×π) to make parity provable, and S8 modernizes deliberately, with before/after shots and re-baselined goldens as its own reviewable change.

The API contract is the spine. The 38 event constants, the BlueprintJS facade, switchView('topview'…) string arguments, the item_type registry, and the save-file schema are frozen for the entire migration. Two private-API leaks the demo commits today (floorplanner.view.draw(), three.getController().setSelectedObject(null)) get proper public APIs (redraw(), clearSelection()) in S6 instead of being copied into Vue.

How much actually moved, measured. Frozen against managed across the ten states: mean absolute difference 0.8 to 5.0 per channel, max 22, and exactly 0 on the 2D canvas. Smaller than "adopt colour management" sounds, and concentrated exactly where the theory puts it. sRGB is close to a power law, so for an unlit textured surface encode(decode(a) × decode(b)) is close to a × b - the walls barely move. What moves is anything with a linear addition in it: the Phong floor is the biggest change in the grid (mean 5.0 on floors, 4.3 on top), because light contributions do not round-trip. The hex material tints move too, which is the ground and the wall fillers.

The one ordering constraint. ColorManagement.getTransfer() does not consult ColorManagement.enabled, so the moment a texture is tagged sRGB the GPU decodes it whatever the flag says. Tag without flipping the output and every tagged surface is a full gamma too dark; flip without tagging and every untagged one is far too bright. The tags and the output space are therefore one commit. The shader includes could go first precisely because they are a provable no-op beforehand - with output in linear space the include expands to an identity - and the parity grid coming back byte-identical is what proves they resolved at all rather than being silently dropped.

Two judgement calls, both written into the code. The wall lightmap is tagged sRGB, which is not three's recommendation for a lightMap and is right for this one: it is a hand-painted vignette, not a baked irradiance buffer. It also preserves the picture, because the walls are unlit and sRGB decode followed by sRGB encode is the identity - the authored 232-253 range passes through untouched. Left linear it compresses to 244.6-254.1 and the vignette flattens from 21 bytes to 9.5, which no scalar lightMapIntensity can undo since the factor varies across the texture. And emissiveColor moves 0x444444 → 0x8d8d8d: the literal is never read back or serialized, so what matters is the linear value it decodes to, and leaving it would have made the hover highlight 4.6× dimmer for no reason anyone chose.

R-01 · The item loader has no failure path high

Both loaders are called with a null onError and nothing around them. A 404, a malformed .glb, or a URL the environment cannot parse dispatches EVENT_ITEM_LOADING and then dispatches nothing at all.

Three things depend on a balance that cannot be relied on: an embedder's loading indicator, Scene.unloadableItemCount, and the app's undo gate — which counts loads in flight and needs an eight-second timer purely to survive a count that never comes back down. SETTLE_BACKSTOP_MS is documented as a backstop; it is really a workaround.

The formatless branch already models the intended fix: dispatch EVENT_ITEM_LOADED with item: null, so every listener counting loads stays balanced whether or not it knows the failure mode exists. That convention does not survive contact with the Controller. Generalising it made Controller.itemLoaded dereference the null immediately:

R-03 · Configuration broadcasts nothing med

Every other mutation in the library announces itself through EventDispatcher. Configuration is a class of static methods over a plain object, so a consumer that wants to react to a unit or scale change has to poll or be told out of band.

That is what killed the settings-panel zoom slider — it read Number(config.scale) off a non-reactive object, rendered 1 once, then sat there reading 1 while the plan was at 300%. It was removed rather than fixed, because there was nothing to hook.

LANDED — P3
  • EVENT_CONFIG_CHANGED, carrying the key, the new value and the old — and only on an actual change. Callers write from watchers and computed setters that re-run for unrelated reasons, so announcing a no-op write turns one user action into a redraw storm and a two-way bound control into a loop
  • Not by extending EventDispatcher: Configuration is a namespace of statics that nobody instantiates, so extending it would mean nothing. One module-level dispatcher with the listener API forwarded as statics gives callers the same addEventListener they use everywhere else
  • This replaced a characterization test asserting the opposite. It described a real gap rather than a quirk worth keeping, so the expectation changed with the code — which is what the preserve-or-fix policy asks for. Wall snapshotting is unchanged: broadcasting a change is not reacting to one
  • The payoff was three stale controls, not the zoom slider. Snap-to-grid, snap distance and grid resolution are writable from the plan overlay too, and the panel read them once at mount. Two tests pin it, and both fail without the fix. The zoom slider stays deleted — it could be made to work now, but the plan has its own readout, stops, fit, wheel and shortcut

R-04 · A texture per wall per redraw, never released high

Edge.updateTexture() runs new TextureLoader().load(url, callback) — a fresh loader and a fresh Texture every call. It is wired to redraw(), which is wired to EVENT_REDRAW. Nothing disposes the old one, so every redraw of a room leaks one GPU texture per wall surface. edge.js:29 loads the shared wall lightmap once per Edge rather than once per scene; Floor does the same for floors.

The 3D view has otherwise-careful disposal — Skybox, Lights, Controller and Main all release properly. Textures are the gap.

LANDED — P3
  • Refcounted per URL, as proposed — but handing out Texture.clone()s rather than one shared Texture. The obvious cache is wrong here: a wall sets repeat from its own width and height, so two walls sharing one Texture would both take whichever set it last. A clone keeps repeat, wrap and colorSpace per surface while .source — the decoded image and the GPU upload behind it — is shared. Verified against three rather than assumed, including that a clone taken before the image lands still receives it
  • Two further leaks surfaced. Floor never removed its EVENT_CHANGED listener, and Floorplan3D.redraw() discarded floors with removeFromScene(), which only takes them out of the scene graph — so every edit that rebuilt the plan left another subscribed floor holding another texture. Floorplan3D had no dispose() at all, so a torn-down viewer stayed subscribed to the model and redrew a scene it no longer belonged to
  • Six tests. The one that matters redraws every edge five times and asserts the handle count does not move; putting the missing release back makes it read 58 where it should read 18

R-05 · The 2D canvas repaints inside pointermove med

There is no requestAnimationFrame anywhere in the 2D path — the only one in the library is Main's render loop. view.draw() is called synchronously from fourteen sites, three reached from the pointermove handler. Every mouse movement is a full canvas repaint on the input thread, and on a large plan that is where dragging starts to feel heavy.

LANDED — P6
  • Fourteen sites was the count of call sites, not of repaints. A drag reaches all three of the pointermove draws on every single event — updateTarget, then the pan branch, then the drag branch — so a press and three moves cost ten full canvas repaints, not four. Measured rather than reasoned about: the no-frame-clock test asserts the exact number, so the figure this paragraph quotes is under test
  • invalidate() as proposed, plus flush(), which the proposal did not anticipate and the tests immediately needed — without it the only way to wait out a coalesced draw is to await a frame, which is neither synchronous nor deterministic. draw() is deliberately untouched: still immediate, still public, because embedders and the browser tier read the canvas straight after calling it
  • Not mechanical, and not covered by the existing suite. One test failed, which was the behaviour change announcing itself, and it became the proof of the fix rather than a casualty. Twelve new jsdom tests on a hand-driven frame clock (installFrameClock, because jsdom's own rAF fires off a 16 ms timer and every assertion would have been a race) and three more in chromium against the compositor's real one. Verified by making invalidate() synchronous again: eight fail
  • The ResizeObserver notice P5 had to swallow is gone, and so is the swallow. Both observers — FloorplannerView2D's and Main's — resized a canvas from inside the callback watching its own container, which is a layout write during observation and is precisely what ResizeObserver loop completed with undelivered notifications reports. Measuring stays in the callback where it is correct; only the write moved to the frame. tests/browser/setup.js is deleted, so tier 2 now fails on any window error. Proven by putting both defects back and watching the run break

R-06 · The package ships raw source, three as a hard dependency med

main points at src/scripts/blueprint.js and files publishes src/scripts — 47 files, 110 kB packed, unbundled and untyped. LANDED — P2

§ 12 · TECHNOLOGY DECISIONS

Four questions worth asking in August 2026

Three of the answers are "not yet", and the reasons matter more than the verdicts. Sources listed in the footer; all claims dated.

T-01 · ADOPT, CAREFULLY

TypeScript — checkJs, but pin to 6.x, not 7

TypeScript 7.0 went stable on 8 July 2026 — the Go-native compiler, measured at 8–12× faster, VS Code's own full check dropping 126s → 10.6s. npm view typescript version gives 7.0.2 today.

It is the wrong version for this project. 7.0 ships no stable programmatic API — that lands in 7.1, several months out — so typescript-eslint and the template type-checkers behind Vue, Svelte and Astro cannot run on it. With 29 single-file components, losing vue-tsc is disqualifying.

Use typescript@6 + vue-tsc. Revisit 7.x when 7.1 restores the API — the tsconfig.json written now carries over unchanged.

T-02 · WATCH

Vue 3.6 & Vapor — take the bump, skip the hype

3.6 hit RC on 18 July 2026 with Vapor feature-complete and a reactivity core rewritten on alien-signals; stable expected Q4. Vapor drops the virtual DOM for opted-in components and reports 2–4× on render-heavy trees.

This app will barely notice. Its cost is canvas rasterisation and WebGL, not vDOM diffing — the shell is a rail, a dock and a status bar.

Take 3.6 when stable, for the reactivity and memory improvements, which are free. Vapor is not the lever here; R-05 is.

T-03 · HOLD

three.js WebGPU — do not migrate yet

WebGPURenderer is still marked experimental in r185. WebGLRenderer remains the recommendation for WebGL2 applications, though it is now in maintenance — no larger features planned, and the nodes/TSL material system is WebGPU-only going forward. A slow-moving cliff, not a present risk.

Worth recording: render_profile.js, written for the classic/studio split, is precisely the abstraction a backend swap would use, and the renderer is constructed in one place behind a factory the tests already stub. When WebGPU stabilises this is a contained change — an argument the profile abstraction earned its keep.

T-04 · ADOPT — THE REAL GAP

Vitest 4 browser mode

Browser mode went fully stable in Vitest 4, with visual regression via toMatchScreenshot and Playwright trace support built in. It is already installed — vitest@4.1.10 is in the tree.

Ten of the seventeen suites run under jsdom, where canvas.getContext('2d') is a stub that records call names and WebGL is a renderer stub. The 2D view's actual pixels have never been rendered in a test, and the studio profile has never been composited in one. The npm run parity harness does drive real Chrome — manually, and calibrated against the classic profile the app no longer uses.

Caveat from the docs, worth designing around: screenshots are environment-sensitive (fonts, GPU, browser build), so baselines must be captured in the same container CI runs and stored per platform.

The proposed gate ladder

Built around the standing constraint that Actions minutes are worth conserving. The design principle: push the cheap, high-yield checks to the developer's machine where they cost nothing, and spend runner minutes only on what genuinely needs a runner.

TIER 0 · LOCAL PRE-COMMIT — 0 ACTIONS MINUTES, ~2s ON STAGED FILES — BUILT
  • ESLint on staged .js / .vue — errors block, the 28 deliberate warnings do not, matching what npm run lint does in CI
  • vitest related --run --passWithNoTests on the staged files' suites
  • npm run typecheck — a whole-project check on every commit, however many files were staged. It is the one task here that cannot take a file list: tsc checks a program, and handing it individual paths makes it ignore tsconfig.json and answer a different question from CI. Under two seconds, so there is no reason to want the cheaper wrong answer. That is why the lint-staged config moved out of package.json into lint-staged.config.mjs — only a function task can decline the appended paths
  • Via simple-git-hooks (lighter than Husky, one dev dependency) plus lint-staged, installed by "prepare": "simple-git-hooks". Two wrong turns worth recording, because both looked right and neither was: a prepare wrapper that skipped when CI was set did nothing, since the dependency's own postinstall had already written the hook and honours SKIP_INSTALL_SIMPLE_GIT_HOOKS rather than CI; dropping prepare and leaving it to that postinstall then failed the other way, because npm runs a dependency's postinstall only when the dependency is actually installed, so npm install on an unchanged tree left no hook. prepare runs every time, the CLI honours the same variable the postinstall does, and the workflows set it on the install step — one variable, both paths. All three cases verified from clean clones

TIER 2 · WHAT WAS DROPPED, AND WHY

No toMatchScreenshot. The tier was specified with screenshot diffing and it is not there. Two reasons, and the second is the one that would still hold with unlimited time:

  • A baseline cannot honestly be produced here. Reference images are environment-bound — font rasterisation, GPU and browser build all move the bytes, which is why Vitest names them per platform and why its own documentation asks for a container. CI is Linux; this machine is macOS with no Docker. Committing a macOS baseline gives the Linux runner nothing to compare against, and the first CI run would fail creating one — with no way to retrieve it, because this workflow deliberately uploads no artifacts
  • Pixel assertions are the better test for this content anyway. What these tests want to know is "does the grid draw in the grid colour" — a contract, checkable by reading a known coordinate and comparing it to the palette value the library exports. That is deterministic everywhere, stores nothing, and when it fails it names the wrong colour instead of reporting that 0.3% of pixels moved

What screenshots would add over this is CSS and layout regression across the chrome, which the pixel tests do not cover. That is real, and it is the case for revisiting — with a containerised baseline job, so the reference is generated in the same environment that compares it. Until then npm run parity remains the visual-diff tool, and it is still manual and still calibrated against classic.

The asset half of P6 done

The gap row said “the .glb models carry no Draco or meshopt compression”, and that framing turned out to be looking at the wrong thing. The 165 models hold 5.2 MB between them. The textures hold 9.8 MB, and 6.6 MB of that sat in 23 PNGs with no alpha channel at all — photographs and baked lightmaps in a lossless container. The other 152 PNGs carry real transparency, are catalog thumbnails, and total under 1 MB. There is no cleverness in the fix: PNG is the wrong container for continuous-tone imagery, and re-encoding 21 of those files as JPEG took public/ from 15.03 MB to 10.62 MB — a 29% reduction in everything served, against maybe 15–20% for Draco on geometry that is a third of the weight.

LANDED — P6
  • Quality is measured, not asserted. Garden clears 38.0 dB at 3434 kB → 844 kB; the baked model maps run 37.8–47.3 dB. A test fails any conversion under 36 dB, so the floor is enforced rather than remembered
  • The finding that changed the scope: rooms/textures/ is a public URL contract.   • Budgets ratcheted down, which is a direction a budget almost never moves. public-total 16.5 → 11.16 MB, demo-total 24 → 18.12 MB; leaving the old ceilings would have handed the next change 4 MB of slack it did not earn.   • A characterization test had to be re-read rather than re-baselined. “Copies textures byte-for-byte rather than re-encoding them” is a claim about the S3 converter — that it ran in Node with no canvas round-trip — and that claim is untouched. One theme: nothing owns anything

RM-002 fixed seven specific defects. This is the pattern underneath them, and it is a single one — the library has no concept of ownership, so nothing knows what it is responsible for releasing, replacing, cancelling or identifying.

The load-bearing sentence in this document is that these are not five problems. A resource leaks because no object was ever declared its owner; a stale callback lands because no load was ever declared current; a room loses its name because identity was derived instead of assigned; undo re-downloads a sofa because history has no unit smaller than the document. What this program is not. It is not a rewrite, and §18 says so at length and with guardrails. H-1 · Nothing disposes geometries or materials high

RM-002 R-04 fixed textures, thoroughly and with a refcounted cache. It did not touch geometries or materials, and the grep is stark: the entire src/ tree contains three geometry.dispose() or material.dispose() calls — two in three/controller.js:108–109 and one in three/skybox.js:208. Ten classes have a dispose(); Edge, Item, Room, HalfEdge, HUD, Scene, Model and Floorplan have none.

The worst offender is the model layer, which the documentation says holds no GPU resources at all. docs/architecture.md:71–74 states the model classes “hold no DOM node, no canvas and no GPU resource”, and blueprint.js:200–203 repeats it as the reason dispose() leaves the model standing. Both are wrong: Room.generatePlane() and generateRoofPlane() build a Mesh each (room.js:147, 159), and HalfEdge.generatePlane() builds a third (half_edge.js:240). They are invisible hit-test planes, which is presumably how they escaped the description — but a ShapeGeometry is a ShapeGeometry whether or not you can see it, and these are added to the live three scene by Floor.addToScene().

The replaced objects hold three meshes between them and go out of scope holding their geometry and material. Combine this with H-4's twenty-five dispatches and opening a four-wall file abandons roughly 150 meshes, geometries and materials before the first frame is drawn.

The view layer leaks the same way, more visibly. Edge.remove() (edge.js:85–97) detaches three listeners and releases both textures — carefully, and that part is R-04's work — and then disposes none of the six meshes an Edge builds. Edge.redraw() calls removeFromScene() and immediately rebuilds, so every EVENT_REDRAW abandons another six. removeFromScene() is also asymmetric with addToScene(): it clears planes and basePlanes but not phantomPlanes (edge.js:118–132). Nothing pushes to phantomPlanes today, so it is latent rather than live — but it is the kind of latent that a debugging aid switched on for an afternoon turns into a duplicate-mesh bug.

Floor.dispose() (floor.js:188–194) detaches its listener, removes from the scene and releases the texture. The floor's ShapeGeometry, the roof's fan geometry and both materials survive. Floor.redraw() (floor.js:47–53) rebuilds both planes without disposing the pair it is replacing.

Item is the one with the clearest single defect. Item.removed() is an empty method (item.js:461–463), so Scene.removeItem() (scene.js:128–139) releases nothing at all: not the merged BufferGeometry, not the glTF materials or the textures GLTFLoader created for them — which never entered the refcounted cache and so are not covered by R-04 — not the two CanvasTextures, two PlaneGeometrys and two materials the dimension labels use, and not wirematerial. And one object is not merely undisposed but left in the scene: initObject() does this.scene.add(this.bhelper) (item.js:452–453) and nothing anywhere removes it. Delete a chair and its selection box remains a child of the three scene, holding a BoxHelper that points at an object no longer in the graph. errorGlow is milder but the same shape: createGlow() clones the entire item geometry (item.js:669) and hideError() only removes it from the scene.

The shared-cache boundary is now genuinely wrong, and the code says so. Main.dispose() ends with an unconditional clearTextureCache() (main.js:525), whose own comment reads: “Acceptable while two simultaneous viewers are not a supported configuration; it becomes R-02's problem when they are.” P7 made them supported and shipped tests/browser/two-designs.test.js to prove it. Disposing one viewer now empties the cache under every other live viewer on the page — each of which re-fetches and re-decodes every image it is still using on its next redraw. That is the exact condition the comment was written against.

DECISION — A REGISTRY PER OWNER, NOT MORE dispose() CALLS
  • Rejected: audit every construction site and add a matching dispose. That is what the current code is an attempt at, and it has three call sites and ten leaks. The failure mode is structural: redraw() paths construct in one method and discard in another, so the pairing is invisible at both ends. Adding thirty more calls produces thirty more places to forget one
  • Rejected: a scene-graph walk at teardown (scene.traverse, dispose everything found). It cannot see anything already detached — which is precisely what leaks here — and it will happily dispose a geometry another viewer is still drawing with
  • Chosen: an explicit ResourceRegistry, owned per viewer. Every geometry, material and texture is registered when created and released as a unit at a declared boundary. Shared entries are refcounted, which the texture cache already does correctly and is the model to copy. three's own guidance is the justification for taking this seriously: “three.js can not automatically clean these resources up… it's up to you to manage them”, and removing an object from the scene does not free anything
  • The ownership question the registry forces us to answer is the real deliverable. Floor.addToScene() adds this.room.floorPlane — a mesh built by the model, added by the view, owned by neither. Either the model owns hit-test geometry and the view borrows it, or the model stops building meshes. A0 picks the first, because the second changes picking

H-3 · Item callbacks have no generation token high

Scene.addItem()'s loaderCallback closes over scope and pushes into scope.items (scene.js:199–212). Nothing records which document asked. Open design A with thirty items, then open design B while they are in flight: clearItems() empties the list, and thirty callbacks then resolve into B, adding A's furniture to B's scene and dispatching thirty EVENT_ITEM_LOADED. useHistory's settle gate counts those (useHistory.js:353–359), so the count it uses to decide when a restore has finished is measuring two documents at once. The same race covers New, Undo, Redo and viewer disposal.

The cancellation primitive already exists in the installed engine, and the library does not use it. three r185's LoadingManager has an abort() (three.core.js:44231) and FileLoader composes it — AbortSignal.any([this._abortController.signal, this.manager.abortController.signal]) at three.core.js:44620. GLTFLoader takes a manager and passes it down to its FileLoader and TextureLoader. But Scene constructs new GLTFLoader() and new OBJLoader() with no manager at all (scene.js:37–38), so every loader in every scene on the page shares the global DefaultLoadingManager — one shared abort surface for all documents, which is the same thing as none.

H-6 · Undo is a document reload med

useHistory is well built and its own docblock argues the case honestly: snapshots cannot be subtly wrong, and command inverses for Corner.mergeWithIntersected would be a library rewrite. That reasoning was right when it was written and it is why A3 is staged rather than a rewrite. But the cost is now measurable: apply() calls loadSerialized() (useHistory.js:247–256), so every undo replays the entire load path — 25+ EVENT_UPDATED, a full 3D teardown per dispatch, and every item re-fetched, re-merged and re-uploaded. Undoing a corner nudge re-downloads the sofa. The count-based settle gate and its 8-second backstop (useHistory.js:84, 217–232) exist to manage exactly this.

There is also a fidelity gap already documented at docs/architecture.md:224–228: saveFloorplan() writes only corners its walls reach, so a corner with nothing attached is not in a snapshot and cannot be restored by one.

H-8 · Assets are unhashed, and their URLs are a published contract med

168 catalog entries resolve to 165 .glb and 3 .gltf files, alongside 154 PNGs and 48 JPEGs under public/. Vite's documentation is explicit about what that directory means: assets there are “copied to the root of the dist directory as-is” — they do not enter the build graph and they never get hashed filenames, unlike imported assets which do. So the entire 10.62 MB payload is served under stable, unversioned names with no content addressing, and a changed model keeps its URL.

The obvious fix is unavailable, and that is the finding. These URLs are not internal: they are bare relative strings composed at runtime (index.html:13–31 explains why they must stay relative) and they are serialized into saved designs — model_url on every item, newFloorTextures[].url on every custom floor. P6 discovered the same thing about rooms/textures/ and built tests/asset-integrity.test.js to defend it. Hashing the filenames would break every document already saved. The indirection has to sit between the logical name in the file and the physical URL on the network, which is what an AssetResolver is.

Beyond caching, the gaps are: no availability policy (a 404 reaches R-01's failed() path and becomes a console line), no integrity, no preload or prefetch of likely items, no CDN-relocatable base, and no per-asset budget — P6 added a per-file ceiling on the tree, which is a different question from “what does placing this chair cost”.

Explicitly out of scope, restated from P6. Draco, meshopt and KTX2 are all supported by three r185's loader family and none is wired in. They remain the right next step for the geometry third of the payload and they are not part of A5, which is about delivery architecture rather than compression. A5 makes them cheap to add later by putting a manifest between the catalog and the network; it does not add them.

Guardrails — what not to do

Written as prohibitions because the failure mode of a program like this is well known: it starts as six sprints and becomes a rewrite in the third one.

DO NOT
  • Do not introduce a parallel model layer. No model2/, no “new” Floorplan beside the old one, no adapter between two representations of the same design. Every sprint edits the existing classes in place. Two model layers means every bug has to be found twice and the migration never finishes
  • Do not convert the library to TypeScript. The JavaScript decision is the user's and it stands; checkJs per file is the mechanism, and P2's ledger in tsconfig.json is the roadmap for extending it
  • Do not make ChangeSet the only signal. The legacy events keep firing. A sprint that would “clean up” by removing EVENT_UPDATED has broken every embedder to save a dispatch
  • Do not delete Floorplan3D.redraw(). It stays as the reference implementation that incremental projection is diffed against. It is also the fallback if K-4 bites
  • Do not replace snapshot history with commands. Commands are layered over checkpoints. The snapshot is the thing that cannot be subtly wrong and it is never removed
  • Do not rename an asset, ever. tests/asset-integrity.test.js exists because P6 nearly did. The resolver adds indirection; it does not license renaming
  • Do not edit a characterization expectation to make a sprint pass. RM-001 §01's ledger governs. A failure is a signal; retiring an expectation is a deliberate act with a changelog line
  • Do not lower a coverage threshold or a size budget. Both are ratchets. This is already written into vitest.config.mjs and tools/budget.json and applies here without exception
  • Do not batch two sprints into one commit range. Each must be independently revertible, because K-1 and K-4 are the kind of risk that surfaces a week later

Typed ChangeSet and incremental projection

doneH-42 weekshard dep: A0

Objective. Let the model say what changed, and let each consumer react to only its own kind — so that dragging a corner stops rebuilding the world and stops moving the camera.

ScopeExcluded
The ChangeSet contract and its six kinds · an adapter deriving today's events from it · incremental Floorplan3D · 2D repaint on geometry kinds · camera recentring gated on extent Removing any legacy event · stable ids (A3 — A2 addresses entities by current reference, A3 upgrades to ids) · a general reactive graph · the 2D view's whole-canvas repaint, which is correct for a canvas

The contract

ChangeSet { topology # corners/walls added, removed, reconnected — rooms may be re-derived geometry # existing entities moved or resized — room set unchanged surface # textures, colours, materials — no geometry implication items # furniture added, removed, moved selection # what is selected — never a model mutation view # configuration, units, render profile, palette } each kind carries the affected entities and a `reason` — 'load' | 'edit' | 'undo' | 'derive' consumers: Floorplan3D topology → rebuild affected · geometry → update transforms surface → swap material · items → nothing Main camera topology only, and only when the plan extent moved 2D view topology, geometry, surface, selection history any kind with reason 'edit', at the gesture boundary autosave the same boundary

  1. Define the contract and the adapter together. The adapter is what keeps K-8 at zero: every legacy event is derived from a ChangeSet, and a test walks the tables in docs/events.md row by row asserting each still fires with its payload
  2. Batch the load path. newCorner() and newWall() stop calling update() unconditionally; loadFloorplan() wraps the whole build in one batch and emits one topology change. This alone takes M-4 from 25 to 1
  3. Gate the camera. Main subscribes to topology changes and recentres only when the plan's extent actually moved. The user-visible fix in this sprint
  4. Incremental Floorplan3D. Rebuild only the Edges and Floors named by the change; release the replaced ones through A0's registry. This is why A0 is a hard dependency — incremental rebuilding without disposal converts one big leak into a continuous one
  5. Keep redraw() and diff against it. A debug mode runs both and compares the resulting scene graph. Not shipped enabled; run in CI on the fixture designs
  6. Fix the removeCorner/removeWall asymmetry while the call graph is open
RATIONALE · ALTERNATIVES · COMPATIBILITY
  • Why a typed set rather than more event constants. More constants multiply the subscription surface and still cannot express “these three walls”. The payload is the point, not the name
  • Alternative rejected — a reactive dependency graph (signals, or an observable store). Real power, wrong shape: it would mean model objects become proxies, and docs/architecture.md's identity warning exists because === comparisons in room detection and EventDispatcher dedup break silently under proxies
  • Alternative rejected — dirty flags on entities. Cheaper, and it is roughly what needsUpdate already is. It cannot express why, so the camera still cannot distinguish a load from a drag
  • Alternative considered — extend update()'s existing two booleans. Honest and small, and it is the fallback if this sprint runs long. It does not give consumers a payload
  • Compatibility. Purely additive. The one observable difference is frequency: EVENT_UPDATED fires once per load instead of 25 times. That is the K-2 risk, and a test asserting a dispatch count is exactly the sort that gets retired deliberately, with a changelog line
ACCEPTANCE · OBSERVABILITY · DoD

  • M-5 = 0. Dragging a corner triggers no full Floorplan3D.redraw() and no centerCamera()
  • Every row of docs/events.md still fires, with its documented payload, asserted individually
  • The incremental path matches the reference. For each fixture design and each edit kind, incremental and full redraw produce the same scene graph — same mesh count, same materials, same transforms

  2. IndexedDB implementation. IndexedDB's quota is a share of disk rather than a fixed few megabytes
  3. Keep a small synchronous pointer in localStorage, and justify it rather than assume it: this is K-6. pagehide cannot await a promise, so the pointer records “a draft exists, at this key, at this timestamp” while the body lives in IndexedDB. Kilobytes, synchronous, always completes
  4. Quota, corruption and rollback. Quota exceeded prunes older drafts before giving up; an unreadable record is treated as no draft, which is what readDraft already does; a store at an unknown version is left untouched and reported rather than migrated speculatively
  5. Reuse A1's pipeline. A recovered draft is a document like any other — parse, validate, migrate, swap. No second loading path

  1. AssetManifest: logical name → {url, bytes, hash, kind}, generated by the existing pipeline in asset-pipeline/ and committed. It is a build artefact of tooling that already exists

  3. Availability as a policy, not a console line. The resolver knows what should exist, so a missing asset is a typed failure through A1's structured result and the UI can name the item
  4. Preload and prefetch. The manifest carries sizes, so the catalog can prefetch likely items at idle priority and the loading indicator can show real progress
  5. Integrity where it is worth it. Hashes are in the manifest; enforcement matters for a CDN deployment and not for same-origin public/. Recorded and made available, not switched on by default
  6. Per-asset budgets beside P6's per-file and per-tree ceilings: the download, decode and GPU cost of placing one catalog item

  • Alternative rejected — move assets out of public/ into the build graph. Gets hashing for free and breaks every saved design, plus the deliberate relative-URL arrangement index.html documents
  • Alternative rejected — Cache API / service worker. Better offline story, much larger surface, and a service worker's update semantics are their own project
  • Alternative considered — keep localStorage and cap the draft size. One line, and it makes the failure quieter rather than rarer
  • Compatibility. Existing drafts are read once from localStorage and migrated to IndexedDB. Asset URLs in saved files are unchanged, which is the point of the sprint

Inside the 165 .glb files the split is 4.67 MB of geometry, 0.41 MB of JSON, and zero embedded images — every texture in this catalog is an external file, which is what makes the two halves separable at all. So the payload is 44.0% geometry and 49.2% pixels, and the two halves need opposite treatments: geometry is already 59.4% compressed by transport and wants a format change to gain more, while pixels are 96.8% incompressible over the wire and are paid in full on every load.

Two facts about the geometry make the first half unusually tractable, and neither needs a codec:

  • Every vertex attribute in the catalog is float32. Not most — all of them, across POSITION, NORMAL and TEXCOORD_0. A furniture model spans a couple of metres; storing its positions to 24 bits of mantissa is precision nothing downstream can use, and KHR_mesh_quantization exists for exactly this
  • Every uint32 index buffer is twice as wide as it needs to be. 410 primitives declare 32-bit indices; all 410 have fewer than 65,536 vertices, and the largest primitive in the entire catalog has 1,174. That is 152 KB recoverable by changing one field, with no visual difference of any kind and no new dependency. Corrected by the B1 trial: 152 KB is the RAW figure and the served saving is 13 KB. Three zero bytes in every four is exactly what gzip already eats — this document's own warning about headline ratios, applied to everything except this sentence.

Why the target for M-12 is left blank. Draco, meshopt and KTX2 all have well-known typical ratios and none of them has been run against this catalog. Quoting a published ratio as a target here would be exactly the failure this document's method exists to avoid, and it would be quoting it against a payload that gzip has already taken 32% of. B1's first task is the trial that produces the number; the budget ratchets to what the trial earns.

The constraint that shapes this sprint. A saved design names its models by URL, and A5's whole argument was that those URLs are a published contract. Changing a file's contents keeps that contract; changing its name or its decoder requirement does not. A build that ships a Draco-compressed .glb under the same name has silently made every older build unable to open documents that were saved before this program — the manifest's kind and a per-entry decoder hint are what keep that from happening, and they are the reason A5 built it.

The blocker A3 named is real, and it is worse than "two walls between one pair is conceivable". It is reachable through the ordinary API with no guard anywhere:

  • Floorplan.newWall() (floorplan.js:374) pushes a wall with no duplicate check. Calling it twice on the same pair produces two walls whose getUuid() is the same string
  • It survives the save format. Two records written, two walls rebuilt, one distinct getUuid() — because loadFloorplan() (floorplan.js:837) calls newWall() once per record and the guard it would need does not exist there either
  • Direction matters and must not. newWall(a,b) and newWall(b,a) give getUuid() values that differ as written and are equal when sorted. A seed that does not canonicalise gives the same wall two identities depending on which way it was drawn; a seed that only canonicalises collides on the duplicate case. It needs both: sort the pair, then add an ordinal

Not in any fixture. None of the three fixtures contains a corner pair with two walls, so this collision has no coverage today and cannot be caught by extending the corpus. It needs a constructed case, and that case is the sprint's real test rather than an afterthought — the failure mode of getting it wrong is two walls that share an id, which is the collision A3 removed from rooms, reintroduced one layer down.

§ 23 · COMPATIBILITY & NON-GOALS

What must not change

§18's guardrails carry over verbatim and are not restated. What follows is what this program adds to them.

  • A design saved by 2.0.0 opens in 2.0.0 after this program. Not "opens in the version that ships it" — opens in the one that came before. Asset contents may change; asset names, and the set of names a build can resolve, may only grow
  • No asset is deleted or renamed. A re-encoded model is an addition, and the manifest is what makes the old name keep working. This is the load-bearing constraint on B1 and it comes straight from H-8
  • No new runtime dependency without a budget line. A Draco decoder is roughly 200 KB of WASM; loading it eagerly would undo the payload win it enables. Corrected: 200 KB is the raw wasm. Gzipped, three's glTF-only decoder is 74.8 KB — 63.2 for the wasm and 11.6 for its wrapper. If it ships, it ships lazily and behind the resolver, and it gets its own budget entry
  • Wall ids stay out of the save file. B2 reconstructs them on load from data the file already has, for the same reason A3 kept room ids unpersisted: a file identifies a wall by its corners, and that is a description another build can read
  • No threshold comes down. Coverage floors and size budgets are ratchets. A5 established what happens when one bites, and the answer was tests

Explicitly out of scope

  • An asset pipeline anybody has to run to develop. Re-encoding is a deliberate, committed operation with its output in the tree, exactly as make-asset-manifest.mjs is. A checkout must build and run with no extra tooling installed
  • The remaining 367 library type errors. B3 takes the SFC tier and the two deletion clusters. three/main.js alone is 108 errors and is a sprint of its own, if it is ever worth one
  • A duplicate-wall guard in newWall(). B2 makes the collision survivable; deciding whether two walls between one pair should be preventable at all is a modelling question, not an identity one
  • Progressive or streamed loading, and a service worker. Both are real answers to payload and neither is this program

Objective. Reconstruct a wall's id on load from the corner pair the file already contains, so that wall selection survives an undo and wall-bound items stop reloading — the two consequences A3 named when it deferred this.

ScopeExcluded

Tasks

  1. Write the two collision tests first, because neither case exists in any fixture: a wall drawn b→a must get the same id as the same wall drawn a→b, and two walls between one pair must get different ids that are stable across a reload. Both fail before the change
  2. Seed from the sorted pair plus an ordinal. Sorting is what makes direction irrelevant; the ordinal is what makes the duplicate case survivable. The ordinal is the wall's position among the walls sharing that pair, in file order — which is stable across a round trip because saveFloorplan() writes this.walls in array order and loadFloorplan() rebuilds in file order. Worth checking rather than assuming: a wall missing a corner is skipped on save (floorplan.js:682), so the ordinal is stable among walls that survive, which is the only set it has to be stable across
  3. Reconstruct in loadFloorplan(), not in the Wall constructor. A wall built by an editing action keeps its Utils.guide(), exactly as today; only the load path derives. This is the A3 pattern — a first open is a no-op and nothing about editing changes
